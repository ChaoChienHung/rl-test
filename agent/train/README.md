# Train-only STOP/RETRY controller pilot

The current Jev-versus-heuristic baseline chooses `CITED_UNION` or `FULL_CONTEXT` once. This folder defines a **different, sequential** pilot: every retrieved 10-sentence chunk is processed in order. For the current chunk, keep the claim and exactly the same 10 sentences fixed, sample the verifier up to three times, and let a controller choose `STOP` (this chunk is sufficiently resolved) or `RETRY` (resample this same chunk) after draw 1 and draw 2. Finishing a chunk always proceeds to the next chunk; the controller never chooses whether to read it. At draw 3, only `STOP` is available. The policy state contains the claim, the current chunk's 10 evidence sentences, observed verifier outputs and remaining retry count. It excludes gold, later draws and counterfactual outcomes.

For each **FEVER train** claim and chunk, the rollout builder must save three stochastic draws from the exact same prompt. At STOP, save the latest draw's valid citations; process the next chunk until all chunks have been read. Deduplicate the saved citations and run the final verifier once on that selected evidence. `ClaimReplayEpisode` implements this sequence and accepts a final-verifier callback. To compare counterfactual STOP choices, run separate complete episodes with the other choices held fixed and cache each distinct final evidence set's result. The existing 900 FEVER dev claims are evaluation-only and must never be controller training data. A final pass is necessary because an intermediate verdict on a 10-sentence chunk can match the global gold label by chance while lacking the required evidence.

The pilot terminal reward is `FEVER_score − 0.05 × extra_draws − evidence penalties` by default. Missing sentences from a complete gold evidence set cost 0.25 each; selected citations beyond that set's size plus three cost 0.05 each. Use the lowest penalty among complete gold sets that were fully present in the retrieved context; skip evidence penalties when no complete gold set was retrieved or the claim is NEI. These weights are initial experimental choices to freeze before dev evaluation. The reward credits the final evidence-backed output and charges for more verifier calls. It does **not** penalize a retry merely because an intermediate verdict matches gold. An attempted fourth draw is masked, not treated as a learned negative action.

`replay_env.py` implements the bounded episode and reward. It is not an RSI-Jev trainer. Before any GPU training, prepare disjoint train-only rollouts, confirm a differentiable RSI-Jev v2.1 checkpoint loading and optimizer path, and compare against the same heuristic plus a supervised action policy on identical rollouts. RSI-Jev's published training code is tailored to its release tasks, so adapting it to this sequential reward requires an explicit model-integration step. Record seeds, policy probabilities, observed states, actions, counterfactual final outcomes and reward weights for each run. Evaluate once on the frozen dev set after the policy and weights are fixed.

An optional second arm can retry the **unchanged final verifier input** after all chunks are processed. It must use a separate run and matching controls, because its decision state and retry cost differ from a single-chunk retry.
