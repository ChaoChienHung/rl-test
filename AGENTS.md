# Repository conventions

This is the team RL branch for a fact verifier. Read `README.md` for the directory and document map, then `verifier/TODO.md` for current priorities.

## Directory roles

- `core/` has shared reward definitions and interfaces. `retrieval/` builds and queries the FEVER index. `agent/agent_loop.py` is the runnable FEVER search/verify loop; `agent/experiments/toy_scaffold/` contains only synthetic controller work. `agent/data/traces/` holds archived loop traces, `agent/docs/` the trace schema, `agent/tests/` tests, and `agent/TODO.md` the agent checklist. `utils/` has data preparation and shared experiment helpers. Do not recreate a `src/` wrapper.
- `agent/evaluation/results/<method>/` keeps each agent evaluator beside its `runs/<model>/<condition>/<run>/` outputs. Submit `agent/evaluation/eval.sbatch` for `sampling_retry`. It keeps evidence fixed, records all draws and retrieval coverage, and simulates a confidence/NEI stopping rule offline. Do not train a controller on these dev claims.
- `verifier/model.py` contains reusable verifier inference, prompting and scoring logic. `verifier/evaluation/` contains the shared verifier evaluator, single-condition Slurm entry point and `results/`. The completed Base/SFT × direct/CoT sweeps remain saved under `verifier/evaluation/results/`. Archived claim-level predictions are in `verifier/evaluation/results/archive/`.
- `verifier/data/train/` contains committed SFT/GRPO examples; `verifier/data/eval/` has frozen claim IDs. Raw FEVER and the BM25/SQLite index must be downloaded or built locally; follow `verifier/docs/data.md`.
- Each training configuration lives under `verifier/experiments/<config>/` and each attempt under `runs/<run>/`. Submit `verifier/train.sbatch` for SoC training; `TRAIN_SCRIPT` selects a configuration and is required. `OUTPUT_ROOT` can move the experiments root to another shared filesystem. Keep metadata, checkpoint files and logs under `runs/<run>/artifacts/`. Model weights and terminal `.log` files are ignored. Use a new run name; never overwrite an existing run.
- Name training configurations with lowercase hyphens in this order: `<method>-<output>-from-<start>-<model>[-<setting>]-<count>-samples`. Examples: `sft-direct-from-base-qwen3p5-2b-5895-samples` and `grpo-cot-from-sft4695-qwen3p5-2b-no-calibration-kl0-1200-samples`. The final count is the training-set size; `from-sft4695` identifies the starting adapter's SFT size. `pool1200` denotes a larger pre-filter pool; `pilot300` is the teacher-request count while the final `227-samples` records accepted rows. `kl004` means KL beta 0.04. Keep historical metadata values unchanged when moving a run directory.
- The fixed 4,695/1,200 FEVER split is documented by `verifier/data/train/sft/fever-oracle-disjoint-4695/split_manifest.json`; verify it with `python -m utils.build_disjoint_sft_grpo_split --check`. The two SFT jobs and subsequent CoT GRPO jobs have completed on SoC according to the user. Their historical run records remain under the corresponding experiment directories. The CoT GRPO reward uses verdict-harm, evidence and invalid-format terms, with confidence calibration disabled. Keep the fixed 1,200-row second-stage set identical when comparing the two arms.
- `verifier/docs/` records verifier methods and historical results. `verifier/TODO.md` tracks verifier work; `agent/TODO.md` tracks agent work. `verifier/INSIGHT.md` is local and Git-ignored; do not commit it or treat it as a shared source.

## Editing and running

- Run Python modules from the repository root with `python -m ...` where a module is available. Keep Slurm submission commands rooted here. `EVAL_MODEL` specifies the model under evaluation (matching its training configuration name, or `base-qwen3p5-2b`); `EVAL_CONDITION` names the prompt/cap condition; `RESULTS_ROOT` moves the evaluation results root while retaining model/condition/run subdirectories; `RESULT_DIR` selects one exact new run directory. Set only one of the two path overrides. Inspect the current SoC partition and resource limits before submitting.
- Preserve historical `meta.json` values and prediction rows as records of the original run. Update current code and documentation paths rather than rewriting their provenance.
- Evaluation result outputs use a hierarchical layout matching training configurations: `verifier/evaluation/results/<eval_model>/<condition>/<run>/`, where `<eval_model>` is the training configuration name (e.g. `sft-direct-from-base-qwen3p5-2b-5500-samples` or `base-qwen3p5-2b`) and `<condition>` is `<prompt>-cap<output-tokens>` (e.g. `direct-cap1024`, `cot-brief-cap1024`, `cot-native-cap1024`). Flat legacy results are preserved under `results/`. Internal prompt-style IDs remain `direct`, `cot_brief`, `cot_chain`, `cot_sft`, `cot_native`.
- Compare experiments with the same claim IDs, model, retrieval condition and evaluator. Record seed, revision, resources, predictions, metrics and logs for each run.
- Update `README.md`, `verifier/TODO.md` and relevant `verifier/docs/` pages when commands, layout or experiment assumptions change.
- Do not commit raw datasets, indexes, checkpoints, credentials or terminal logs. Do not push or submit cluster jobs unless the user requests it.
